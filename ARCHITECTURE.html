Architecture overview

P1 API Monitor

Watches ServiceNow P1 incidents, alerts the right people in Teams and email, and gives SWAT teams one shared board to coordinate on, from first alert through resolution. Its data is kept in Azure Storage, so nothing is stored on the server.

15 minDefault check interval
3States tracked: In Progress, On Hold, Resolved

Why it helps

What changes for the people who respond to P1 incidents.

⚡

Faster awareness

New, escalated or re-opened incidents reach Teams and email within one check interval. Nobody has to watch the dashboard.

🛡️

Nothing silently dropped

Each check compares against the last known state. An alert that no channel accepts is retried on the next run.

🧭

One shared view

The SWAT board shows In Progress, On Hold and Resolved incidents with filters and counts, so everyone works from the same data.

📝

Intake after resolution

Resolved and on-hold incidents stay on the board, so teams can still complete the intake form, RCA and notes afterwards.

🤖

Unattended

Calls the ServiceNow REST API with an OAuth client credentials token. No browser, no Okta login, no MFA prompts.

📦

Portable

Runs as one Docker container configured by a single .env file. The data is in Azure Storage, so the container can be moved or rebuilt without losing it.

System overview

Data flows left to right. Alerts go out, and the board reads and writes the same saved state. The app signs in to Azure Storage with its managed identity, which needs the Storage Blob Data Contributor role on the storage account.

What happens every check

Each run is the same five steps, so the results are predictable.

  1. Query ServiceNowRead every incident in In Progress, On Hold and Resolved through the Table API, page by page.
  2. Compare with the saved listFind incidents that are new, changed priority, or moved to On Hold or Resolved since the last run.
  3. Alert the channelsSend a Teams card and an email for each change. An alert counts as delivered when at least one channel accepts it.
  4. Save the outcomeStore the new state with a timestamp. Keep On Hold and Resolved incidents. Remove the ones that were closed or canceled.
  5. Retry what failedAn alert that no channel accepted is not recorded, so the next run sends it again.

Incident lifecycle

How one incident moves through the monitor and onto the board.

In Progress

New alert sent. Shown under In Progress.

On Hold

Update alert sent. Kept on the board with the time it changed.

Resolved

Update alert sent. Kept for intake forms and RCA.

Reopened

Back to In Progress. Alerted again as new.

Closed or canceled

Removed from the saved list and the board.

Priority changes while In Progress trigger a separate alert, so a P2 escalated to P1 is visible immediately.

Where the data lives

Three kinds of data in one Azure Storage folder hold everything the monitor and board need.

🗃️
incidents.json
Tracked incidents with last-known state, priority, and when the state last changed.
✅
swat_status.json
Which teams are Required, who joined each team, and who recorded it and when.
📝
swat_details/
One file per incident with intake answers, RCA, timestamped notes and version history.

Each one is a blob in the container and folder set in .env (AZURE_STORAGE_CONTAINER and AZURE_STORAGE_FOLDER). The app reaches the storage account with its managed identity, which holds the Storage Blob Data Contributor role on that account. No key or connection string is stored. The deployment script creates the container and folders, and grants the role. Everyone who uses the board reads the same data, and the container keeps nothing locally.

Security boundaries

What the tool can and cannot do.

Read-only to ServiceNowThe monitor only reads incidents. It never changes them. Login is OAuth only, with no user password.
Secrets stay out of filesThe OAuth client secret, webhook URLs and SMTP passwords are environment variables only. Storage access uses a managed identity, so there is no storage key to store or rotate.
Least privilegeNon-root container. Needs outbound HTTPS and SMTP only.
Limit the boardNo login on port 8080. Restrict it to the network or put it behind an authenticated proxy.
